# 설명 모션 만들기 (ppt 형식)

질문이나 요청을 받아 그 주제를 큰 그림부터 설명하는 발표 화면을 만드는 방법이다. 읽는 사람은 이 스킬을 실행하는 에이전트다.
이 문서와 시작 틀 폴더(`<스킬 폴더>/engine/explainer/`)만 보고 처음부터 끝까지 만들 수 있게 썼다. 엔진 구조와 발표 모드 동작은 `reference/engine.md`, 확인 요령은 `reference/qa.md` 에 있고 여기서는 다시 쓰지 않는다.

## 파이프라인과 꼭 지킬 것

질문이나 요청을 받아 그 주제를 큰 그림부터 설명하는 발표 화면을 만든다. 클릭으로 한 컷씩 넘기고, 컷은 10개 안팎이다.
시작 틀은 `<스킬 폴더>/engine/explainer/` 이다(장면 2, 컷 6. 블록 조합과 재사용을 설명한다). 엔진 구조는 `reference/engine.md` 와 같고, 장면 파일 계약은 그 폴더의 `CONTRACT.md` 에 있다.

새 시안의 엔진은 `<스킬 폴더>/engine/explainer/` 에서 복사한다.
자세한 방법은 이 문서의 아래 절에 있다.

| 단계                      | 할 일                                                                                                                                                                                                                                                                 | 끝났다고 볼 기준                                                |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| 1. 리서치                 | 주제를 조사한다. 레포의 파일과 문서를 먼저 보고 모자라면 웹을 본다. 조사한 사실과 근거를 상세 문서 `source.md` 한 개에 적는다.                                                                                                                                        | 주장마다 근거(파일 경로와 기준 커밋, 또는 출처 주소)가 있음     |
| 2. 큰 그림 초안           | 분석은 깊게 하되 설명은 가장 바깥쪽 큰 그림부터 한다. 10컷 안팎의 장면표와 컷마다 자막 1개를 `source.md` 에 적는다. 채팅에는 출력하지 않고 승인도 받지 않는다. 문장은 제작 전에 근거와 대조한다(codex 사실 대조).                                                     | 장면표와 문장이 `source.md` 에 있고 사실 대조를 통과            |
| 3. 사전 테스트(필요할 때) | 볼 사람이 주제를 얼마나 아는지 요청에서 알 수 없으면 3문제를 낸다. 반드시 AskUserQuestion 도구로 묻는다. 볼 사람을 요청에서 알 수 없으면 같은 호출에 볼 사람을 묻는 문항 1개를 추가한다(문항은 모두 4개까지). 결과로 수준을 정해 초안의 낱말, 비유, 코드 양을 맞춘다. | 수준(처음, 조금 앎, 잘 앎)과 문제와 답을 `source.md` 에 기록    |
| 4. 제작                   | 시작 틀의 발표 모드 엔진을 복사해 장면을 그린다. 화면의 UI 조각은 `kit.ui`(`ui.css`)로 그리고 도식 요소의 색은 팔레트(`kit.W`)로 정한다. 사물이나 비유를 그린 그림은 직접 그리지 않고 반드시 codex 에 요청해 그린다.                                      | 컷마다 프레임을 저장해 직접 봄, 페이지 오류 0건, 초점과 자막 규칙(8절) 확인                 |
| 5. 컷 수 확인과 검증      | 컷(읽는 멈춤)이 8~12개인지 확인한다. 화면만 보는 역할 검증과 사실 대조를 한다.                                                                                                                                                                                        | 컷 수, 코드가 보이는 컷, 남은 문제를 보고                       |
| 6. 이어 묻기              | 완료 보고 바로 뒤에 AskUserQuestion 으로 더 궁금한 것이 있는지 묻고, 질문은 질문 창의 직접 입력(Other)에 적게 한다. 질문이 오면 같은 세션에서 새 설명 모션으로 만들지, 대화로 답할지를 다시 AskUserQuestion 으로 묻고 선택대로 진행한다.                              | 사용자가 "없음"이나 "나중에 묻기"를 선택(질문 창을 닫아도 마침) |

- 사전 테스트는 초안을 만든 뒤 제작 전에 한다. 볼 사람의 수준을 전혀 알 수 없으면 초안보다 먼저 해도 된다. 요청에 수준이 적혀 있으면 건너뛴다.
- 요청한 사람은 주제의 내용을 모르는 경우가 많다. 리서치 결과, 장면표, 문장을 채팅에 출력해 승인받지 않고 바로 제작한다. 제작 전에 사용자에게 묻는 것은 사전 테스트뿐이다.
- 완료 보고에는 여는 주소, 컷 수, 코드가 보이는 컷, 검증 결과, 남은 문제만 적는다. 장면표와 문장은 다시 출력하지 않는다.
- 이어 묻기는 반드시 AskUserQuestion 도구로 하고, 채팅에 글로 묻고 턴을 끝내지 않는다.

**꼭 지킬 것(설명 모션)**

1. **볼 사람을 먼저 정한다.** 누가 보는지와 그 사람이 주제를 얼마나 아는지에 따라 표현을 정한다.
   - 코드를 모르는 사람에게는 그림과 익숙한 비유(레고 블록 같은 것)가 설명을 맡는다. 코드는 그림을 다 보여 준 뒤 1~2컷에만 작게 넣는다.
   - 코드를 아는 사람에게는 실제 파일 이름, 코드, 수치를 넣는다.
2. **큰 그림부터 말한다.** 첫 컷 자막은 주제 종류에 따라 정한다. 깊은 내용은 `source.md` 에 두고, 더 궁금한 것은 본 사람이 에이전트에게 묻는다.
   - 진행 보고나 결과 설명이면 첫 컷 자막이 결론이다.
   - 개념 설명이면 무엇인가부터 시작하고, 첫 컷 자막이 그 개념을 한 문장으로 정의한다.
3. **한 컷에 자막 1개와 초점 1개만 둔다.** 자막은 화면 아래 한 줄이고 주장 하나를 완결 문장으로 말한다. 그림은 그 주장의 근거이고, 시선이 갈 초점은 컷마다 하나다. 같은 대상이 장면마다 다시 나오게 한다.
4. **UI 조각은 ui.css 로 그린다.** 버튼, 배너, 입력 필드 같은 UI 조각은 직접 그리지 않고 `kit.ui` 로 `ui.css` 의 컴포넌트(`mx-` 클래스)를 불러온다. 간격, 모서리, 글자 크기는 그 컴포넌트의 값을 그대로 쓰고 배율만 정한다. `kit` 으로 그리는 도식 요소(박스, 화살표, 선, 카드)의 색은 팔레트 값(`kit.W`)만 쓴다.
5. **문장의 범위를 넓게 쓰지 않는다.** 우리 제품의 방식이면 주어를 그렇게 쓴다("리액트 컴포넌트는" 대신 "우리 제품의 배너 블록은"). 수치는 세는 기준과 기준 커밋을 `source.md` 에 적는다.
6. **화면 요소 이름은 표준 용어로 쓴다.** 박스, 텍스트, 버튼이 그 예다.
7. **화면만 보는 검증을 한다.** 원문을 모르는 역할(볼 사람과 같은 수준 1개 이상)이 컷 그림만 보고 내용을 쓰게 하고 `source.md` 와 대조한다. "코드를 읽지 못해도 이해되는가"를 꼭 묻는다.
8. **넘기기는 클릭으로만 한다.** 자동 전환은 화면의 체크박스를 켰을 때만 동작한다.
9. **그림은 반드시 codex 가 그린다.** 에이전트가 SVG, CSS, canvas 로 사물이나 비유를 직접 그리지 않는다.
    - 대상: 사물이나 비유를 그린 그림이다(탈것, 장비, 건물, 사람 같은 것).
    - 대상이 아닌 것: 박스, 화살표, 선, 판, 이름 태그, 카드 모양 아이콘 같은 도식 요소(`kit` 부품)와 UI 조각(`kit.ui`)이다. UI 조각을 담는 틀도 `kit` 부품이다.
    - codex 를 쓸 수 없으면(설치나 로그인 문제, 한도) 직접 그리지 않고 멈춰서 사용자에게 알린다.
    - 방법은 이 문서의 "그림은 codex 로 그린다" 절에 있다.
10. **끝나면 질문을 받는다.** 완료 보고 뒤 AskUserQuestion 으로 더 궁금한 것을 묻고, 질문이 오면 같은 세션에서 새 설명 모션으로 만들지 선택지로 묻는다.
    - 방법은 이 문서의 "6단계 이어 묻기" 절에 있다.

## 1. 한눈에

| 단계            | 만드는 것                                              | 사용자 확인 지점                                                     |
| --------------- | ------------------------------------------------------ | -------------------------------------------------------------------- |
| 1. 리서치       | 상세 문서 `source.md`                                  | 없음(볼 사람을 알 수 없으면 사전 테스트에서 함께 물음)               |
| 2. 큰 그림 초안 | `source.md` 의 장면표와 컷별 문장                      | 없음(채팅에 출력하지 않고, 사실 대조를 통과하면 바로 제작)           |
| 3. 사전 테스트  | 문제 3개와 판정 (필요할 때만)                          | 사용자가 AskUserQuestion 으로 직접 답함                              |
| 4. 제작         | 장면 파일, 단계 표, codex 로 그린 그림 파일(`assets/`) | 컷마다 프레임을 직접 보고 보고                                       |
| 5. 검증         | 컷 수, 역할 검증, 사실 대조 결과                       | 보고서 확인                                                          |
| 6. 이어 묻기    | 받은 질문과 선택의 기록, 선택하면 새 시안              | 사용자가 AskUserQuestion 의 직접 입력에 질문을 적고 다룰 방법을 선택 |

결과물은 `source.md`(근거와 예상 질문), `scenes/s<n>.js`(장면마다 한 파일), 장면 수와 단계와 칩 문구를 채운 `motion-steps.js` 와 `index.html`, `README.md`(여는 법, 장면표, 그린 것, 실제와 다른 점, 검증 결과), 레포 밖에 저장한 확인용 프레임 PNG 다.

## 2. 시작하기

1. 폴더를 사용자가 정한 위치에 만든다(예: `motions/<주제>/`). `ui.css` 가 `index.html` 과 같은 폴더에 있어야 하므로 `engine/explainer/` 의 구조를 바꾸지 않는다.
2. 시작 틀에서 엔진을 복사한다. 장면 파일(`s1.js`, `s2.js`)은 시작 틀의 예시 장면이므로 새로 쓴다. 그림 파일(`assets/`)도 새 주제의 것은 codex 로 새로 그린다.

```bash
SK=<스킬 폴더>
NEW=<모션 폴더>
mkdir -p $NEW/scenes $NEW/tools
cp $SK/engine/explainer/{index.html,motion-steps.js,click-fx.js,export.mjs,baseline.mjs,ui.css,CONTRACT.md} $NEW/
cp $SK/engine/explainer/scenes/kit.js $NEW/scenes/
cp $SK/engine/explainer/tools/check.mjs $NEW/tools/
cp $SK/engine/explainer/scenes/s1.js $SK/engine/explainer/scenes/s2.js $NEW/scenes/   # 장면 파일의 모양을 보고 새로 쓸 때 시작점으로 쓴다
```

3. 화면 디자인은 `examples/explainer-demo/` 를 기준으로 한다. 색, 칸 모양, 큰 숫자, 단계 원, 박스 흐름, 끝 화면은 그 예시의 장면 파일에서 가져다 쓰고 새로 디자인하지 않는다.
4. 복사한 뒤 바꿀 곳은 아래와 같다. `motion-steps.js` 와 `index.html` 은 `[기능마다]` 표시 부분만 바꾼다.
   - `motion-steps.js`: `FEATURE_ID`, `SCENES`, `STEPS_SRC`, `CAPTIONS`, `CAPTION_OF`, `CAPTION_SCENES`
   - `index.html`: 8행 주석, `ASSET_V`, 장면 파일 목록(`scenes/s1.js` 부터 장면 수만큼), 장면마다 `#scene<n>{--fig-dy:0px}`(장면 안 그림만 아래로 옮기는 값)
   - 색을 바꾸려면 `scenes/kit.js` 의 `kit.W` 와 `ui.css` 맨 위 `--mx-*` 변수를 함께 바꾼다.
5. Playwright 는 `<스킬 폴더>/reference/usage.md` 의 Playwright 준비 절을 따라 모션 폴더에 설치한다.

## 3. 1단계 리서치

**조사할 내용**

- 정의: 그것이 무엇인지
- 구성: 어떤 요소로 이루어지는지
- 동작: 어떻게 움직이고 어떻게 쓰는지
- 차이: 비슷한 다른 것과 무엇이 다른지
- 실제 예: 우리 제품에서 쓰는 곳

**조사할 곳**

- 프로젝트의 파일과 문서를 먼저 본다.
- 모자라면 웹을 본다. 출처 주소를 `source.md` 에 적는다.

**source.md 형식**

| 순서 | 절               | 내용                                                                                     |
| ---- | ---------------- | ---------------------------------------------------------------------------------------- |
| 1    | 제목과 날짜        | 문서 제목, 작성일, 근거로 쓴 파일 경로 목록                                              |
| 2    | 대상과 목표      | 누가 보는지, 본 뒤 무엇을 설명할 수 있어야 하는지, 근거 기준 커밋, 처음 나오는 용어 풀이 |
| 3    | 한눈에           | 장면표(칩, 컷별 자막)와 화면에 나오는 코드 목록                                 |
| 4    | 근거 절          | 장면마다 한 절이고 주장, 근거 파일 경로, 원문 인용을 적는다                              |
| 5    | 단순화한 표현    | 모션에서 실제와 다르게 그린 곳                                                           |
| 6    | 확인하지 못한 것 | 확인하지 못했다고 그대로 적는다. 지어내지 않는다                                         |
| 7    | 예상 질문        | 화면에 넣지 않은 내용과 본 사람이 물을 만한 질문의 답, 근거 경로                         |

- 주장마다 근거(파일 경로와 기준 커밋, 또는 출처 주소)를 붙인다.
- 수치는 집계 방법과 기준 커밋을 함께 적는다. 예를 들어 한 폴더의 tsx 파일을 전체 읽어 컴포넌트 사용 횟수를 집계했으면 폴더 경로와 기준 커밋을 적는다.
- JSX 사용 횟수를 줄 단위 검색으로 세면 여러 줄에 걸친 태그를 빠뜨린다. 파일 전체를 읽어 집계한다.
- 일반 설명과 이 레포의 사례를 구분해 쓴다. 이 레포에서 확인하지 않은 말을 레포의 사실처럼 쓰지 않는다.

## 4. 2단계 큰 그림 초안

분석은 깊게 하되 화면은 가장 바깥쪽 큰 그림에서 시작해 안쪽으로 간다. 깊은 내용은 `source.md` 에 둔다.

**장면 후보 (바깥쪽에서 안쪽 순서)**

- 무엇인가, 어떻게 이루어지나, 어떻게 쓰나, 다른 것과 무엇이 다른가, 왜 좋은가, 우리 제품과 어떤 관계인가
- 주제에 맞는 4~5개를 장면으로 삼는다. 장면 하나가 칩 하나다.
- 장면마다 컷 2~3개, 전체 8~12컷이다. 컷은 읽는 멈춤(`hold` 단계) 하나이고, 멈춤은 3.2~3.6초다.
- 컷 하나에 자막 하나다. 자막은 장면 안에서 첫째, 둘째, 셋째 컷 순서로 나온다. 셋째 컷은 코드에 한정하지 않고 장면의 마무리, 변형, 결과를 보인다. 코드를 보이는 장면은 셋째 컷에서 코드를 본다.
- 첫 장면은 주제 종류로 나눈다.
  - 진행 보고나 결과 설명: 첫 컷 자막이 결론이다(예: 현재 도달한 수준).
  - 개념 설명: 무엇인가부터 시작하되 첫 컷 자막이 그 개념을 한 문장으로 정의한다.
- 마지막 컷 자막은 결론이나 다음 할 일이다. 끝 화면은 "끝" 한 글자다(아래 "끝맺음과 끝 화면").

**장면표 형식과 예시 (`source.md` 의 한눈에 절에 적는다. 칩 역할은 짧은 이름, 칩 제목은 질문 형태)**

| 장면 | 칩                                      | 컷별 문장                                                                                                                                                 | 그림                                                                    |
| ---- | --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 1    | 컴포넌트, 컴포넌트는 무엇인가요         | 컴포넌트는 블록을 끼워 만든 화면 조각 하나입니다 / 박스 안에 아이콘과 텍스트를 담으면 배너 컴포넌트가 됩니다 / 리액트는 컴포넌트를 조합해 화면을 만드는 도구입니다 | 박스, 아이콘, 텍스트 블록 3개가 끼워져 배너 블록이 됨, 배너 블록 하나에 이름표 |
| 2    | 조합과 분리, 컴포넌트끼리 어떻게 쓰나요 | 컴포넌트끼리 조합하면 화면이 됩니다 / 블록은 하나씩 분리되어 있어서, 같은 블록을 다른 화면에도 조합할 수 있습니다                                         | 블록 5개를 모달 화면 판에 조합하고 같은 배너 블록을 두 번째 판에도 조합 |


**문장 규칙**

- 한 컷에 자막 1개다. 자막은 화면 아래 한 자리(y 924, 40px 700, 가로 가운데)에 한 줄로 나오고 컷마다 같은 자리에서 바뀐다. 폭은 1640px 안에 들어간다(길면 32px 까지만 줄이고, 그래도 넘치면 문장을 줄인다).
- 주장형 완결 문장으로 쓴다. 주제 이름("컴포넌트")이 아니라 말하려는 결론("이렇게 만든 블록 하나가 컴포넌트입니다")을 쓴다.
- 컷당 주장은 하나다. "그리고"로 주장 두 개를 잇지 않는다. 두 개이면 컷을 나눈다.
- 자막만 이어 읽어도 이야기가 되는 순서로 쓴다. 결론이나 정의가 앞에 오고, 근거, 결과, 다음 할 일이 뒤따른다.
- 하이라이트(`marks`)는 컷마다 1~2곳이고 주장의 핵심 낱말이나 구절이다. 색은 blue(흐름과 단위), green(마침과 반영), yellow(남음과 주의)다.
- 범위를 넓게 쓰지 않는다. 우리 제품의 방식이면 주어를 그렇게 쓴다("리액트 컴포넌트는" 대신 "우리 제품의 배너 블록은").
- 화면 요소는 표준 용어로 쓴다. 박스, 텍스트, 버튼, 아이콘을 쓰고 상자, 글자, 단추를 쓰지 않는다.
- 수는 아라비아 숫자와 단위로 쓰고, 화면 문장에 가운뎃점, 꺽쇠, 줄표를 쓰지 않는다.

장면표와 문장은 채팅에 출력하지 않고 승인도 받지 않는다. 요청한 사람이 주제의 내용을 모르는 경우가 많기 때문이다. 대신 제작 전에 문장마다 근거와 대조한다. codex 에 문장 목록과 조사 자료를 주고 사실과 다른 곳, 범위를 넓게 쓴 곳을 찾게 하고, 필수 지적을 반영한 뒤 바로 제작한다. 사용자가 문장을 직접 정해 주면 그 문장은 글자 그대로 쓴다.

## 5. 3단계 사전 테스트

**시점과 방법**

- 볼 사람이 주제를 얼마나 아는지 요청에서 알 수 없을 때 한다. 요청에 수준이 적혀 있으면 건너뛴다.
- 볼 사람이 요청한 사람과 다르면 "볼 사람이라면 어떻게 답할지" 기준으로 답해 달라고 안내한다.
- 반드시 AskUserQuestion 도구를 쓴다. 채팅에 문제를 글로 쓰고 답을 받지 않는다.
- 볼 사람을 요청에서 알 수 없으면 같은 호출에 볼 사람을 묻는 문항 1개를 추가한다(문항은 모두 4개까지).
- 도구를 한 번 호출해 문제 3개를 낸다. 초안을 만든 뒤 제작 전에 하고, 볼 사람의 수준을 전혀 알 수 없으면 초안보다 먼저 해도 된다.
- 주제의 핵심 개념을 쉬운 문제부터 낸다. 낱말을 들어 봤는지, 구성 요소의 관계를 아는지, 실제로 써 봤는지(또는 비슷한 것과의 차이를 아는지) 순서다.
- 선택지는 4개이고 마지막은 "잘 모르겠다"다. 정답이 하나인 문제로 만든다. 정답 위치는 문제마다 바꾼다.

**예시 (리액트 주제)**

| 문제                              | 정답                                                                                | 틀린 선택지                                                          |
| --------------------------------- | ----------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| 리액트에서 컴포넌트는 무엇입니까? | 화면의 일부를 이름 붙여 만들어 두고 여러 곳에서 쓰는 단위                           | 화면 전체를 이미지로 저장한 파일 / 서버에 데이터를 저장하는 프로그램 |
| props 는 무엇입니까?              | 컴포넌트에 전달하는 값                                                              | 컴포넌트를 삭제하는 명령 / 화면 색 이름 목록                         |
| HTML 과 리액트는 무엇이 다릅니까? | HTML 은 화면마다 같은 조각을 다시 작성하고, 리액트는 만들어 둔 컴포넌트를 불러 쓴다 | 둘은 같고 이름만 다르다 / 리액트는 그림만 그린다                     |

**판정**

| 맞힌 문제 | 수준    | 표현 방식                                                             |
| --------- | ------- | --------------------------------------------------------------------- |
| 0~1개     | 처음    | 그림과 비유를 중심으로 쓴다. 코드는 0~2컷이다. 낱말마다 풀이를 붙인다 |
| 2개       | 조금 앎 | 그림과 실제 이름을 쓴다. 코드는 2~4컷이다                             |
| 3개       | 잘 앎   | 실제 코드와 수치를 중심으로 쓴다. 비유는 줄인다                       |

- 문제, 사용자의 답, 정답, 판정 수준을 `source.md` 의 대상과 목표 절에 적는다.
- 판정 수준에 맞춰 초안의 낱말, 비유, 코드 양을 수정한다. 채팅에 다시 출력하지 않는다.

## 6. 4단계 제작

**장면 파일과 엔진**

- 화면 디자인은 `examples/explainer-demo/` 를 기준으로 한다. 색, 칸 모양, 큰 숫자, 단계 원, 박스 흐름, 끝 화면은 그 예시의 장면 파일에서 가져다 쓰고 새로 디자인하지 않는다.
- 엔진(`index.html`, `motion-steps.js`)이 칩, 장면 전환, 발표 모드, 시간 계산을 맡는다.
- 장면 파일은 `MotionScenes.register(n, { build, render, rings, measure })` 로 자기 장면의 요소를 만들고 프레임마다 그린다. 계약 전문은 새 폴더의 `CONTRACT.md` 에 있다.

| 구분                        | 파일                                                                                                                |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 고친다                      | `scenes/s<n>.js`, `motion-steps.js` 의 `[기능마다]`, `index.html` 의 `[기능마다]` 와 `ASSET_V`                      |
| 부품이 모자랄 때만 추가한다 | `scenes/kit.js` (기존 부품은 고치지 않는다)                                                                         |
| 고치지 않는다               | 나머지 `index.html`, `motion-steps.js` 의 공용 부분, `click-fx.js`, `export.mjs`, `baseline.mjs`, `tools/check.mjs` |

**단계 표 쓰는 법**

- 그리는 움직임은 `scroll` 단계, 읽는 멈춤은 `hold` 단계, 장면 전환은 `trans` 단계로 쓴다.
- 단계 id 는 `s<n>_in`, `s<n>_hold`, 그 뒤로 컷마다 움직임 단계, `s<n>_sentence1`, `s<n>_read1`, 다음 컷의 움직임 단계, `s<n>_sentence2`, `s<n>_read2` 순서다. 셋째 컷은 같은 모양으로 `s<n>_sentence3` 과 `s<n>_read3` 를 추가한다. 읽는 멈춤(`read`)은 3.2~3.6초다. 코드를 보이는 컷은 앞에 `s<n>_code` 를 둔다. 자막 교체는 `kit.captions` 가 `sentence` 단계와 같은 번호의 `read` 단계를 보고 정한다.

**컷 그림 규칙 (발표 기준)**

- 컷마다 초점은 하나다. 초점은 `kit.FOCUS` 의 밝은 채움(`bg`)과 굵은 테두리(`edge`)로 칠한 한 덩어리이고, 나머지는 `kit.DIM`(0.45) 불투명도나 회색 윤곽으로 둔다. 컷이 바뀔 때 앞 컷의 초점은 DIM 으로 내리거나 사라지게 한다.
- 초점 색의 뜻은 정해 둔다. blue 는 흐름과 단위, green 은 마침과 반영, yellow 는 남음과 주의다.
- 자막 하이라이트는 컷마다 1~2곳이다. 초점 색과 같은 색을 쓴다.
- 그림 글자는 28px 이상이다. 코드 카드의 코드 글자(22~24px)만 예외다.
- 그림 글자는 이름과 숫자와 짧은 라벨만 쓴다. 자막의 서술문을 그림에 다시 쓰지 않는다(라벨이 자막 낱말과 같은 것은 괜찮다).
- 초점 채움 위의 글자와 체크는 `FOCUS` 의 `ink`, 무대 바탕 위의 색 글자와 선은 `text` 를 쓴다.
- 이름표는 가리키는 그림 바로 옆에 둔다. 범례나 번호로 오가며 찾게 하지 않는다.
- 그림 덩어리는 y 100~880 안에 두고, 아래 끝은 자막 가까이(y 820~870)에 두는 것을 권장한다. 위가 크게 비면 가운데에 둬도 된다.
- 지워도 주장이 전달되는 그림 요소는 넣지 않는다.
- 근거 출처는 Mayer와 Fiorella(2014)의 신호, 일관성, 공간 근접 원리, Alley의 문장형 제목과 시각 근거 방식(Garner와 Alley 2013), Duarte의 3초 이해와 결말 권고, W3C WCAG 1.4.3 대비 기준(4.5 대 1)이다.
- Duarte와 Minto 같은 책의 권고는 2차 요약으로 확인한 것이므로 인용할 때 그렇게 밝힌다. 그림 글자 28px 은 이 출처들이 정한 값이 아니라 이 스킬이 정한 값이다.

**끝맺음과 끝 화면**

- 마지막 컷 자막은 결론이나 다음 할 일 하나다.
- 끝 화면(`#endCover`)은 "끝" 한 글자다. 마지막 컷에서 한 번 더 누르면 나오고, 이전을 누르면 마지막 컷으로 돌아온다. `?box=1`, `?export=1`, `?embed=1` 에서는 숨는다.
- 아래 진행 숫자(`3 / 6` 같은 현재 컷과 전체 컷)가 발표 모드의 진행 표시다.

| `kit.pose`, `kit.moveAlong`, `kit.appear`, `kit.show`, `kit.prog`, `kit.sub` | 이동, 곡선 이동, 나타남, 불투명도, 단계 진행값 0~1                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |

- 인자와 반환값은 `scenes/kit.js` 의 부품 위 주석과 `CONTRACT.md` 에 있다. 쓰기 전에 읽는다.

**UI 조각 그리기**

- 버튼, 배너, 입력 필드 같은 UI 조각은 직접 그리지 않는다. `kit.ui` 로 `ui.css` 의 컴포넌트를 불러온다.
- `kit.ui(root, { x, y, w, h, s = 1, html })`
  - `x, y`: 무대 좌표
  - `w, h`: 확대 전 실제 크기(px)
  - `s`: 확대 배율(왼쪽 위 기준)
  - `html`: `mx-` 클래스로 쓴 마크업
- 돌려주는 요소는 `kit.pose`, `kit.moveAlong`, `kit.show` 로 움직인다. `el._b` 는 `{ x, y, w: w*s, h: h*s }` 다.
- 요소에 쓰는 함수는 다음과 같다.
  - `el.setHtml(html)`: 마크업을 바꾼다.
  - `el.resize(w, h)`: 확대 전 크기를 바꾼다(돌기가 있으면 다시 놓는다).
  - `el.moveTo(x, y)`: 자리를 바꾼다.
  - `el.natural()`: 마크업의 확대 전 내용 크기 `{w, h}` 를 돌려준다(measure 안에서만 쓴다).
- 요소 안에 shadow root 를 만들어 `ui.css` 를 불러온다. 무대의 "#stage 안 div 는 모두 position:absolute" 규칙이 마크업에 영향을 주지 않게 하기 위해서다.
- CSS 를 다 불러오기 전에는 프레임을 그리지 않는다(`window.ready` 가 `kit.uiReady()` 를 기다린다). `kit.ui` 와 이 함수를 쓰는 부품은 `build` 안에서만 부른다.
- 아이콘은 `kit.icon(name, size)` 가 만든 SVG 문자열이다(`display:block`, 이름 `info` `check` `warn`). `kit.iconSvg(tone, size)` 는 tone 의 아이콘 이름으로 `kit.icon` 을 부른다.

```js
// 배너 마크업을 직접 쓸 때: 아이콘은 kit.icon(이름, 크기)
const bannerHtml = `<div class="mx-Banner" data-tone="warning"><span class="mx-Banner__icon">${kit.icon('warn', 20)}</span><div class="mx-Banner__body">텍스트</div></div>`;
const raw = kit.ui(root, { x: 480, y: 520, w: 480, h: 49, s: 2, html: bannerHtml });

// 배너는 보통 부품으로 만든다(tone 5가지). 폭은 measure 에서 el.fit() 으로 글 폭에 맞춘다
const banner = kit.banner(root, { cx: 960, y: 520, s: 1.7, tone: 'warning', text: '텍스트' });
const block = kit.bannerBlock(root, { cx: 960, y: 640, s: 1.7 }); // 돌기를 얹은 배너 블록

// 버튼 블록: h 는 무대 px 높이이고 배율은 h / 40 이다
const save = kit.buttonBlock(root, { x: 1200, y: 800, w: 120, h: 64, text: '저장', variant: 'primary' });
```

- tone 같은 값을 시간에 따라 바꿀 때는 값이 바뀌는 프레임에만 `setHtml` 을 부른다. 같은 `t` 면 같은 마크업이어야 한다.
- 글자 크기는 배율이 정한다. 배너와 sm 버튼의 문구는 14px 이라 무대 글자 크기는 14 곱하기 배율이다. 판을 줄여 쓰면(`kit.pose` 의 `s`) 줄인 배율도 곱한다. 배너 문구가 28px 이상(배율 2 이상), 버튼 문구가 28px 이상(블록 높이 80 이상)이 되게 잡고, 저장한 프레임에서 확인한다.
- 선택과 입력은 `kit.radioBlock`(`mx-Radio` md 를 1.5배로 3개)과 `kit.inputBlock`(`mx-Textarea` 필드)이 블록 몸통 안에 그린다. 몸통 옆 문구는 막대로 줄인다.
- 작은 판 안의 배너와 버튼은 `kit.miniBanner`(문구 없는 배너 블록에 막대)와 `text: null` 인 `kit.buttonBlock`(막대는 장면에서 추가)로 그린다. 글자가 없으므로 글자 크기 기준에서 뺀다.

**그림은 codex 로 그린다**

사물이나 비유를 그린 그림(탈것, 장비, 건물, 사람 같은 것)은 에이전트가 SVG, CSS, canvas 로 직접 그리지 않고 codex 에 요청해 그린다. 방식은 codex CLI 의 이미지 생성이다.

- 대상이 아닌 것: 박스, 화살표, 선, 판, 이름 태그, 카드 모양 아이콘 같은 도식 요소(`kit` 부품)와 UI 조각(`kit.ui`)이다. UI 조각을 담는 틀(리액트 예시의 레고 블록)도 `kit` 부품이다. 이것들은 `kit` 으로 그린다.
- codex 를 쓸 수 없으면(설치나 로그인 문제, 한도) 직접 그리지 않고 멈춰서 사용자에게 알린다.

절차

1. 그림마다 주제문을 쓴다. 무엇을, 어느 방향에서, 무엇을 강조하는지 영어 한 문장으로 쓴다. 제품 이름, 고객 이름, 내부 정보는 넣지 않는다(프롬프트가 외부 서비스로 나간다).
2. 레포 밖 폴더(예: `~/.cache/<작업>/review/`)에 프롬프트 파일을 만든다. 첫 줄은 저장 위치와 형식, 다음 줄은 아래 스타일 고정문, 마지막 줄은 `SUBJECT: <주제문>` 이다. 후보를 2~3장 받으려면 프롬프트 파일을 후보마다 하나씩 만든다.
3. 로그인 상태를 확인하고 후보 수만큼 동시에 생성한다(3장에 약 1분). 대화형 zsh 에서는 별칭을 피하도록 `command codex` 로 실행한다.

```bash
command codex login status   # "Logged in using ChatGPT" 인지 확인
NEW=<모션 폴더>   # 채택 파일 복사에 쓴다
cd <레포 밖 작업 폴더>
mkdir -p assets/candidates review
command codex exec -C "$PWD" --skip-git-repo-check -s workspace-write - < review/prompt-a1.txt > review/codex-a1.log 2>&1 &
command codex exec -C "$PWD" --skip-git-repo-check -s workspace-write - < review/prompt-a2.txt > review/codex-a2.log 2>&1 &
wait
```

프롬프트 파일의 첫 줄과 스타일 고정문(색은 `kit.W` 값)은 다음과 같다. 스타일 고정문은 그림마다 글자 그대로 쓴다.

```text
Generate ONE image and save it as ./assets/candidates/<이름>.png (PNG, 3:2 landscape aspect, highest resolution available). Output nothing else.
STYLE LOCK (follow exactly): clean flat vector-style illustration with simple rounded geometric shapes. Uniform dark outline (#0F172A) with one consistent medium stroke width. Flat fills only. Strict palette: white #FFFFFF, light blue #DBEAFE, blue #2563EB for small accents only, light gray #F1F5F9, gray #CBD5E1, dark #0F172A. No gradients, no textures, no 3D shading, no shadows. PURE WHITE background (#ffffff) with nothing else on it. No text, no letters, no numbers, no logos, no people, no faces. The whole subject is centered with generous white margin on all sides.
SUBJECT: <주제문>
```

사람을 그려야 하면 스타일 고정문에서 `no people, no faces` 를 지우고, 주제문에 얼굴을 그리지 않은 단순한 사람 모양이라고 적는다.

4. 후보를 비교표로 묶어 직접 보고 1장을 채택한다. 후보는 2~3장 받는다.
   - 비교표: 후보 PNG 를 한 장에 나란히 붙인 시트(Pillow 등으로 만든다. 예: `review/sheet.jpg`)를 만들어 직접 본다
   - 버리는 그림: 글자나 숫자가 생긴 그림, 색이 스타일 고정문을 벗어난 그림, 그 물건으로 보이지 않는 그림이다.
   - 채택할 그림이 없으면 주제문을 고쳐 다시 생성한다.
5. 다듬는다. 흰 배경 기준으로 여백을 잘라내고(둘레 5% 여백), median 필터(5)로 색을 줄일 때 생긴 점을 지우고, 가로 1200px 로 줄여 PNG 로 저장한다(약 300KB).
6. 채택한 파일만 시안 폴더의 `assets/` 에 복사한다(예: `assets/example.png`). 후보와 로그는 모션 폴더 밖에 둔다. 새 시안에는 `assets/` 폴더가 없으므로 먼저 만든다(`mkdir -p $NEW/assets`).
7. 장면에서는 `kit.img` 로 흰 카드 위에 놓는다. 그림 배경이 흰색이라 회색 무대 위에 바로 놓으면 흰 사각형이 보인다.
   - 카드 없이 놓을 때는 저장한 프레임에서 그림 둘레에 흰 테두리가 보이는지, 그림 안쪽 흰 면이 뚫려 뒤가 비치는지 확인한다.
8. 그림은 이동, 확대, 축소, 투명도만 움직인다. 따로 움직여야 할 대상(예: 오토바이와 사이드카를 따로 합치는 장면)은 같은 스타일 고정문으로 따로 생성한다.
9. `kit.img` 는 `build` 안에서만 만든다. `index.html` 의 `window.ready` 가 `kit.imgReady()` 를 기다리는지 확인하고, 같은 시각의 프레임을 2번 저장해 같은지 비교한다. 그림을 다 불러오기 전에 그리면 프레임이 달라진다.
10. README 에 그림마다 주제문, 후보 수, 채택 파일을 적는다.

**색 팔레트**

- `kit` 으로 그리는 도식 요소의 색은 `kit.W` 값만 쓴다. `kit.W` 는 `scenes/kit.js` 에 있고 `ui.css` 맨 위 `--mx-*` 변수와 같은 값이다. 바꿀 때는 둘을 함께 바꾼다.
- 간격, 모서리, 글자 크기는 `kit.ui` 로 그린 컴포넌트가 정한다. 도식 요소에 그 값이 필요하면 `ui.css` 에서 확인해 `kit.W` 에 추가한다.
- 장면 파일에서 색 값을 직접 쓰지 않는다. `kit.W` 와 `kit.C` 에 없는 색이 필요하면 `kit.W` 와 `ui.css` 에 추가한다. `kit` 으로 직접 그려도 되는 것은 도식 요소(레고 블록 같은 틀, 화면 판, 이름 태그, 화살표, 막대)뿐이다. 사물이나 비유를 그린 그림은 앞의 "그림은 codex 로 그린다" 대로 codex 로 그린다. 도식 요소도 값은 `kit.W` 와 `kit.C` 만 쓴다.

**코드 카드 규칙**

- 코드는 볼 사람 수준이 허락하는 컷에만 넣는다(수준별 상한은 앞의 판정 표). 코드를 모르는 사람에게는 그림을 다 보인 뒤 1~2컷이다.
- 그림 아래에 그림보다 작은 카드로 둔다. 코드 글자는 22~24px 이다.
- 카드마다 한글 제목과 한글 라벨을 붙인다(예: 제목 "HTML 코드", 라벨 "화면마다 태그 3개를 다시 작성"). 코드를 읽지 못해도 그림과 문장만으로 컷의 뜻이 통해야 한다.
- 코드는 `source.md` 근거 절의 원문 그대로 적고 줄인 부분(class 이름 생략 등)은 README 에 적는다. 화면 텍스트는 `textContent` 로 넣는다(`kit.code` 와 `kit.codeLines` 가 그렇게 한다).
- 코드 컷이 아닌 컷에는 코드(꺾쇠 태그, class, CSS, 중괄호, 고정폭 코드 줄)를 쓰지 않는다.

**움직임 규칙**

- `render(ctx)` 는 `ctx.t` 만으로 그리고 같은 `t` 면 같은 그림이어야 한다. CSS transition, CSS animation, `Math.random`, `Date`, `performance.now` 를 쓰지 않는다.
- 장면 컨테이너가 보이지 않는 동안에는 `render` 가 불리지 않으므로 앞 프레임 값을 기억해 쓰지 않는다.
- 글 폭에 따라 정하는 위치는 `measure(kit)` 에서 정한다. 글꼴을 불러온 뒤 한 번 불린다. 그 전에는 `render` 가 아무것도 그리지 않게 한다.

**위임**

- 장면 파일은 sonnet 에 맡긴다. 엔진 파일(`index.html`, `motion-steps.js`, `scenes/kit.js`)을 고칠 때는 Opus 가 한다.
- 위임 지시에 적을 것: 새 폴더의 `CONTRACT.md` 경로, 사실 대조를 통과한 장면표와 문장(글자 그대로), 고칠 수 있는 파일과 없는 파일, 코드가 들어가는 컷, 화면 요소 표준 용어를 따를 것, advisor 와 리뷰 도구를 부르지 않을 것
- 맡긴 뒤에는 완료 알림만 기다리지 않고 산출물 폴더의 파일 변경 시각(`ls -l`)으로 진행을 확인한다. 장면 파일을 수정하면 `index.html` 의 `ASSET_V` 를 올린다(안 올리면 Aside 로 보는 화면이 예전 파일을 쓴다).

## 7. 여는 법과 확인

서버는 모션 폴더에서 `127.0.0.1` 로 띄운다. `ui.css` 가 `index.html` 과 같은 폴더에 있어 폴더를 서버 루트로 잡으면 된다.

```bash
NEW=<모션 폴더>
python3 -m http.server 8990 --bind 127.0.0.1 --directory $NEW
# 주소: http://127.0.0.1:8990/index.html

cd $NEW
PORT=8990 node tools/check.mjs --steps
```

- 포트는 쓰이지 않는 번호를 선택하고, 다른 서버가 쓰는 포트를 끄지 않는다. 사용자에게 보일 때는 위 주소를 브라우저로 연다.

**tools/check.mjs 환경 값과 옵션**

| 항목              | 뜻                                                                                                                          |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `PORT`            | 서버 포트(기본 8933)                                                                                                        |
| `BASE_PATH`       | 주소의 폴더 경로(기본값 빈 문자열). 서버 루트가 모션 폴더가 아닐 때만 쓴다                                                  |
| `PW_ROOT`         | `node_modules/playwright` 가 있는 폴더(기본은 파일 위치에서 위로 올라가며 찾음). 설치는 `usage.md` 의 Playwright 준비 절 |
| `--steps`         | 단계마다 id, 장면, 종류, 시작과 끝(실제 초)을 출력                                                                          |
| `--times 0.3,3.2` | 시각(실제 초)마다 `f_<초>.png` 저장                                                                                         |
| `--out <폴더>`    | 저장 폴더다. 결과 JSON 도 `check.json` 으로 저장한다                                                                        |

- 통과 기준: 페이지 오류 0건, 콘솔 오류는 `motion-params.json` 404 한 줄뿐, 칩 넘침 없음, `hold` 단계 수가 장면표의 컷 수와 같음
- 이 모션은 반복 재생하지 않아 `--seam` 은 쓰지 않는다.

**컷마다 프레임 저장**

1. `--steps` 출력에서 `hold` 단계의 시작 시각을 확인한다.
2. 시작 시각에 0.3초를 합산한 값들을 `--times` 에 준다. 움직임 중간 프레임도 장면마다 2장 이상 추가한다.
3. 저장한 PNG 를 모두 직접 열어 본다. 저장만 하고 보지 않으면 확인한 것이 아니다.

**볼 것**

- UI 조각이 실제 모양으로 보이는지(스타일이 빠진 맨 텍스트면 `ui.css` 를 못 불러온 것)
- 겹침, 넘침, 잘림, 자막 한 줄, 그림 글자 크기(28px 이상)
- 코드가 정한 컷에만 있는지, 정지 화면만 봐도 뜻이 통하는지
- 컷마다 초점이 하나이고 나머지가 DIM 이나 회색 윤곽인지, 자막 하이라이트가 1~2곳인지(8절 발표 규칙 확인에서 집계)
- 마지막 컷에서 한 번 더 눌렀을 때 "끝" 화면이 나오고 이전으로 마지막 컷에 돌아오는지

**같은 네트워크의 다른 기기에서 보여 줄 때**

- 서버는 평소 `127.0.0.1` 로만 띄운다. 모션 폴더에 `.env.local` 같은 로컬 전용 파일이 있으면 `0.0.0.0` 으로 띄울 때 같은 네트워크에 모두 열린다.
- 공유할 때는 모션 폴더의 실행 파일만(`ui.css` 포함) 복사한 폴더를 만들어 그 폴더를 `0.0.0.0` 으로 띄운다. 문서(`*.md`)와 도구(`tools/`, `*.mjs`)는 복사하지 않는다.

```bash
SHARE=$(mktemp -d)
(cd $NEW && rsync -a --exclude '*.md' --exclude 'tools/' --exclude '*.mjs' --exclude node_modules --exclude .pw-browsers ./ $SHARE/)
python3 -m http.server <포트> --bind 0.0.0.0 --directory $SHARE
# 주소: http://<맥 주소>:<포트>/index.html (맥 주소는 ipconfig getifaddr en0)
```

- 공유가 끝나면 서버를 끄고 복사한 폴더를 지운다. 시안을 고치면 다시 복사해야 보인다.

## 8. 5단계 검증

**컷 수**

- `hold` 단계(읽는 멈춤)가 8~12개인지 집계한다. 범위를 벗어나면 장면표로 돌아가 컷을 줄이거나 늘린다.
- 코드가 보이는 컷의 수와 id 를 적어 둔다.

**발표 규칙 확인**

- 컷마다 자막이 아래 한 줄이고 하이라이트가 1~2곳인지 센다.
- 컷마다 초점(`FOCUS` 채움) 덩어리가 하나이고 나머지가 DIM 이나 회색 윤곽인지 본다.
- 그림 글자가 28px 이상이고(코드 카드 제외) 자막 서술문을 되풀이하지 않는지 본다.
- 자막만 차례로 이어 읽어 결론, 근거, 다음 할 일이 이어지는지 읽는다.
- 마지막 컷에서 한 번 더 누르면 "끝" 화면이 나오고 이전으로 마지막 컷(`n / n`)에 돌아오는지 누른다.

**화면만 보는 역할 검증**

- 역할은 볼 사람과 같은 수준으로 정한다(예: 개발을 모르는 디자이너). 서브에이전트에게 역할을 주고, 원문(`source.md`, 코드, 웹)을 읽지 못하게 한다.
- 컷 프레임 PNG 만 순서대로 준다. 아래 틀을 쓴다.

```text
너는 <볼 사람 역할>이다. 아래 이미지는 발표 화면의 컷이다. 컷 순서는 파일 이름 순서다.
이 이미지만 보고 질문에 답한다. 다른 파일, 코드, 웹을 읽지 않는다.
이미지: <PNG 경로 목록>
질문마다 근거가 된 컷 번호를 적고, 이해하지 못했으면 "모르겠다"라고 쓴다.
<질문 10개>
```

**질문 10개**

1. 이 발표는 무엇을 설명합니까? 한 문장으로 쓰세요.
2. 핵심 개념을 어떤 그림을 보고 이해했습니까?
3. 장면마다 무엇을 말합니까?
4. 화면의 수치는 무엇을 뜻합니까?
5. 우리 제품이나 디자인 시스템과는 어떤 관계입니까?
6. 비유 그림이 그 비유로 보였습니까?
7. 코드가 보인 컷은 몇 개입니까? 코드를 읽지 못해도 이해됩니까?
8. 어려웠던 컷과 이유는 무엇입니까?
9. 뜻을 모르는 낱말과 기호는 무엇입니까?
10. 텍스트가 잘리거나 겹치거나 너무 작은 곳이 있습니까?

- 답을 `source.md` 와 대조해 맞음, 틀림, 모름으로 나눈다. 틀림과 모름이 나온 컷은 그림이나 문장을 수정하고 다시 검증한다.
- 7번이 "읽지 못하면 이해되지 않는다"이면 그 컷은 코드를 줄이거나 그림을 추가한다.
- 통과해도 사용자가 이해한다는 뜻은 아니다. 에이전트는 화면의 텍스트를 읽어 답할 수 있다. 사용자는 완성된 화면을 직접 넘겨 보고 확인한다.

**사실 대조**

- 범위를 넓게 쓴 문장과 수치를 codex 에게 묻고 advisor 에게도 묻는다. 서브에이전트에게 위임한 일이면 이 호출은 메인 세션이 한다.
- 묻는 내용: 문장의 주어가 실제보다 넓지 않은지, 수치의 집계 방법과 기준 커밋이 맞는지, 근거 파일이 그 말을 뒷받침하는지.

**보고 형식**

채팅 보고에는 아래 5가지만 적는다. 장면표와 문장은 다시 출력하지 않는다.

- 여는 주소
- 컷 수와 코드가 보이는 컷 수
- codex 로 그린 그림 수와 파일
- 검증 결과(페이지 오류, 칩 넘침, 역할 검증)
- 남은 문제(실제와 다르게 그린 곳 가운데 알아야 할 것, 확인하지 못한 것)

컷 id 와 시작 시각, 그림마다의 주제문과 후보 수, 저장한 PNG 폴더는 README 에 적는다. 보고 뒤 턴을 끝내지 않고 이어 묻기(9절)를 한다.

## 9. 6단계 이어 묻기

**시점**

- 5단계 검증을 마치고 완료 보고(여는 주소, 컷 수, 코드가 보이는 컷, 검증 결과, 남은 문제)를 채팅에 적은 바로 뒤에 한다. 턴을 끝내지 않고 이어서 한다.
- 반드시 AskUserQuestion 도구를 쓴다. 채팅에 질문이 있는지 글로 묻고 끝내지 않는다.
- 질문 창이 떠 있는 동안에는 앞에 적은 채팅 글이 보이지 않을 수 있다. 질문 문장에 어느 모션에 관한 것인지와 여는 주소를 함께 적는다.
- 질문은 시안 화면의 입력 필드가 아니라 질문 창의 직접 입력에 적는다. 시안 화면에 입력 필드를 넣지 않는다.

**첫 질문(더 궁금한 것이 있는지)**

- 1문항이고 선택지는 2개다. 질문 창에는 이 문항만 넣고 커밋 여부 같은 다른 결정을 같이 묻지 않는다.
  - "없음": 여기서 마친다.
  - "나중에 묻기": 지금은 마치고, 같은 대화에서 질문하면 이어서 한다.
- 질문은 선택지가 아니라 질문 창의 직접 입력(Other)에 적게 안내한다. AskUserQuestion 은 선택지 밖의 글을 늘 직접 입력으로 받을 수 있다.
- 예시 질문 문장: "블록 조합 설명 모션(<여는 주소>)을 보고 더 궁금한 것이 있습니까? 질문은 직접 입력(Other)에 적어 주세요."
- 답 판정
  - 선택지 이름과 다른 글이 오면 그 글이 질문이다.
  - "없음"이면 마친다.
  - "나중에 묻기"면 마치고, 같은 대화에서 질문이 오면 둘째 질문부터 이어서 한다. 뒤에 온 채팅 글이 이 모션을 묻는 질문인지 새 요청인지 애매하면 둘째 질문으로 확인한다.
  - 답 없이 질문 창을 닫으면 도구 호출이 거절되고 턴이 멈춘다. "없음"으로 보고 다시 묻지 않는다. 사용자가 다음 말을 하면 그 말부터 이어서 한다.
  - 직접 입력한 글은 그 문항의 답 값으로 온다고 보고 판정한다. 실제 입력으로는 아직 확인하지 못했으니 처음 받을 때 답의 형태를 확인한다.

**둘째 질문(받은 질문을 어떻게 다룰지)**

- 같은 세션이 그 질문을 이어받아 바로 다시 AskUserQuestion 으로 묻는다. 받은 질문을 질문 문장에 그대로 넣는다.
- 선택지는 2개다.
  - "새 설명 모션으로 제작": 이 질문을 주제로 리서치부터 다시 해 10컷 안팎의 모션을 만든다. 볼 사람과 수준은 앞의 판정을 그대로 쓴다(분야가 달라지면 다시 확인한다).
  - "대화로 답": 상세 문서와 코드에서 근거를 찾아 대화로 답한다.
- 답 판정
  - 답 없이 질문 창을 닫으면 턴이 멈춘다. 새 모션을 만들지 않고, 사용자가 다음 말을 하면 그 말부터 이어서 한다.
  - 직접 입력이 오면 그 글을 지시로 보고 따른다(예: 범위를 좁혀 달라는 글). 뜻이 분명하지 않으면 둘째 질문을 한 번 더 묻는다.

**선택한 뒤**

- 새 설명 모션으로 제작
  - 그 질문을 주제로 1단계(리서치)부터 다시 한다. 새 폴더를 만들고(2절) 앞 시안 폴더에 덧붙이지 않는다.
  - 볼 사람과 수준은 앞 시안의 판정을 그대로 써서 사전 테스트를 건너뛴다. 주제가 앞 시안과 다른 분야면 다시 테스트한다.
  - 앞 시안의 `source.md` 를 먼저 읽어 이미 조사한 근거를 다시 쓴다.
  - 두 시안 README 에 서로의 경로를 적고, 새 시안 README 첫머리에 어느 시안의 어떤 질문에서 이어진 것인지 적는다.
  - 새 모션이 끝나면 다시 이어 묻기를 한다.
- 대화로 답
  - 근거(파일 경로)와 함께 답한다.
  - 답한 뒤 첫 질문으로 돌아가 더 궁금한 것이 있는지 다시 묻는다.

**기록**

- 어느 쪽이든 받은 질문(글자 그대로), 선택, 답의 요지나 새 시안 경로를 앞 시안 `source.md` 의 예상 질문 절 끝에 "실제로 받은 질문" 소제목으로 적는다.

## 10. 함정

- **사실 대조를 통과한 문구는 글자 그대로 쓴다.** 제작 중에 문장과 칩 문구를 바꾸지 않는다. 바꿔야 하면 다시 근거와 대조한다. 사용자가 직접 정한 문구는 바꾸기 전에 묻는다.
- **innerHTML 로 화면 텍스트를 넣지 않는다.** 꺾쇠가 든 글자가 태그로 해석되어 사라진다. `textContent` 를 쓴다.
- **그림을 직접 그리지 않는다.** 사물이나 비유를 그린 그림은 SVG, CSS, canvas 로 직접 그리지 않고 codex 로 생성한다. codex 를 쓸 수 없으면 멈추고 사용자에게 알린다.
- **주제문에 제품 이름, 고객 이름, 내부 정보를 넣지 않는다.** 주제문은 외부 서비스로 나간다.
- **실제와 다르게 그린 곳은 README 에 적는다.** 비유 그림, 줄여 쓴 코드, 예시 수치, 생략한 블록이 해당하고, "뺀 것과 실제와 다른 점" 절에 적는다.
- **이어 묻기를 채팅 글로 대신하지 않는다.** 질문 창의 문장만 보고도 어느 모션에 관한 질문인지 알 수 있게 쓴다.
- **밝은 채움에 DIM 0.28 을 쓰지 않는다.** 밝은 채움이 거의 보이지 않아 0.45(`kit.DIM`)를 쓴다.
- **밝은 채움 위에 흰 체크를 쓰지 않는다.** 보이지 않으므로 `kit.icon('tick', 크기)` 와 진한 색(`FOCUS` 의 `ink`)을 쓴다.
